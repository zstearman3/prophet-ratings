# One-ticket economics

Target one ticket, including all agent work and final gates, within one Plus five-hour usage allowance. This is a consumption target, not five elapsed hours or a fixed token count. Pro availability does not relax the default. User-specified tighter limits take precedence. Skill instructions and coarse account snapshots are a soft policy, not a guaranteed subscription spending cap.

## Checkpoints and reserve

- At start and phase boundaries, read the usage tool when available and record window duration, remaining percentage, and reset time. Select a 300-minute window by its duration rather than assuming primary/secondary order. Respect other applicable windows too. Avoid repeated polling.
- Reserve at least 20 percentage points of the full five-hour allowance as a safety margin. Plan against the remaining headroom above that floor, including reviews, QA, hooks, repairs, and publication. User-provided per-ticket consumption ceilings further limit that headroom. Begin an expensive phase only when the remaining work plausibly fits; the reserve is not a promise about the cost of the next call.
- Account usage includes other chats and may update late. Treat observed consumption conservatively; do not claim exact attribution to this ticket. A reset does not replenish this ticket's allowance or authorize another window. Before crossing a reset with unfinished work, hand off rather than silently start a second allowance. Do not wait out limits, purchase credits, switch billing, or create an automation to continue without instruction.
- If no five-hour window/tool is exposed (including Pro), state that numerical tracking is unavailable. Use the convergence checkpoints below, modest contexts, and a feasibility assessment; do not translate weekly percentages or API token prices into a fictional Plus allowance or claim the target was measured.

## Bound the work

The default is one coordinator, one plan reviewer, one implementer for the whole ticket, one code reviewer, and one QA agent. Branch complexity/simplification assessment belongs to that same code-review pass and repair allowance, with no extra agent or automatic cleanup phase. Use sequential handoffs and fresh contexts for independent gates. Never fork the entire chat into every role. Give each role only the ticket requirements, necessary instructions, relevant plan/evidence paths, and its assignment.

Implementation uses the model the user selected for the active task. Prefer the runtime's model-inheritance mechanism and omit an implementation model override when that preserves the selected model; a fresh context does not justify a cheaper model. An explicit user instruction selecting a different implementer model takes precedence. Record the effective model when exposed, otherwise record verified inheritance without guessing a model name. If inheritance is unavailable, use the selected model identifier supplied by the runtime or user; if it cannot be resolved or that model is unavailable, ask for the implementation model choice before dispatch rather than silently substituting.

Independent plan/code review and QA default to `gpt-6.1-sol` with medium reasoning; explicit user preferences for those roles take precedence. Keep these reviewers independent of the implementer. State implementation inheritance and any reviewer model overrides in the initial plan/handoff. If a reviewer default is unavailable, record a suitable available substitution. If an explicitly requested reviewer model is unavailable, use and record an available fallback only when the user has already authorized it; otherwise ask the user for a model choice before dispatching that role. Never silently substitute an explicitly requested model or omit a required independent role. The selected implementation model does not enlarge the ticket's budget or authorize purchasing capacity.

Track planning revisions separately from implementation repair rounds; both consume actual time/usage, but planning corrections do not consume a code-repair allowance. An implementation repair round groups material findings, applies supported fixes, runs affected verification, and obtains focused follow-up for invalidated gates. Reuse the relevant agents rather than restarting completed phases.

After each implementation repair round, record the acceptance results that improved or regressed, remaining failures, evidence for the next diagnosis, and whether the remaining work plus final gates fits the available budget. Two implementation repair rounds trigger an explicit convergence reassessment, not an automatic stop. Continue within existing authorization when evidence supports a bounded next change and completion remains feasible; a new material finding alone does not mandate a handoff.

If consecutive repairs leave the same acceptance result unimproved without new causal evidence, stop speculative edits and reassess the approach. Resume only with a supported next diagnostic or repair step that fits the remaining budget. Hand off incomplete when the budget/reserve or feasibility no longer supports completion; ask only when progress requires a changed scope, budget or consequential user decision. Never weaken acceptance criteria or waive checks to make a round count look successful.

Do not delegate each small task, run parallel full suites, generate implementation-sized plans, repeatedly fetch unchanged documents, or chase unrelated improvements. Capture long logs locally and provide concise commands/results. Plan review must assess feasibility before implementation. If the full ticket appears too large, present a proposed smaller deliverable or split for agreement; do not silently drop acceptance criteria or create extra tickets.

## Stop with a resumable result

When headroom or the convergence assessment no longer supports completion, stop starting new phases. Safely finish/clean up any already-running command; do not terminate a data operation unsafely. Preserve worktree, plan, findings, commands/results, completed/pending gates, and the next concrete action. Keep the ticket out of Testing/Done and do not publish a PR presented as ready. Budget pressure never permits weaker assertions, skipped required hooks/reviews/QA, or unresolved material defects.
